# Programmatic Usage (API)

In case your use case involves programmatic usage of the functionality provided by `license-kit`, you can use the `@callstack/licenses` package. This package exposes the core functionalities of the license management tool, allowing you to integrate it into your Node.js applications.

## Installation

To get started, install the package using your preferred package manager:

<PackageManagerTabs
  command={{
    npm: 'npm install -D @callstack/licenses',
    pnpm: 'pnpm add -D @callstack/licenses',
    yarn: 'yarn add -D @callstack/licenses',
    bun: 'bun add -d @callstack/licenses',
  }}
/>

## Usage

### Basic Usage

```typescript
import {
  generateAboutLibrariesNPMOutput,
  generateLicensePlistNPMOutput,
  renderLicenseExpression,
  scanDependencies,
  Types,
} from '@callstack/licenses';
import * as md from 'ts-markdown-builder';

// apart from dependencies, also include devDependencies, but only from the root package.json;
// also, include all transitive dependencies & optional dependencies
const optionsFactory: Types.ScanPackageOptionsFactory = ({ isRoot }) => ({
  includeDevDependencies: isRoot,
  includeTransitiveDependencies: true,
  includeOptionalDependencies: true,
});

// scan dependencies of a package
const licenses = scanDependencies(packageJsonPath, optionsFactory);

// generate AboutLibraries-compatible JSON metadata
const aboutLibrariesCompatibleReport = generateAboutLibrariesNPMOutput(licenses);

// generate LicensePlist-compatible metadata
const licensePlistReport = generateLicensePlistNPMOutput(licenses, iosProjectPath);

// generate a Markdown report
const markdownString = md
  .joinBlocks(
    Object.entries(licenses)
      .flatMap(([packageKey, { name: packageName, version, author, description, license, licenseFiles, url }]) => [
        md.heading(packageName, { level: 2 }),
        '\n',
        `Version: ${version}<br/>\n`,
        url ? `URL: ${url}<br/>\n` : '',
        author ? `Author: ${author}<br/>\n\n` : '',
        licenseFiles.map(({ licenseId, file, content }) => `${licenseId ?? file}:\n\n${content}`).join('\n\n'),
        '\n',
        description ? `Description: ${description}\n` : '',
        `License: ${renderLicenseExpression(license)}`,
        '\n',
        md.horizontalRule,
      ])
      .join('\n'),
  )
  .toString();
```

### Options

As you can see in the example above, filtering for the packages to be included in the scan for dependencies is based on the passed in `ScanPackageOptionsFactory`. This factory would be invoked for every scanned `package.json` file, including the root and any considered dependencies and - given a `ScanPackageOptionsFactoryPackageInfo` object informing of the context of the package being scanned - should produce an accompanying configuration that would filter this package's dependencies.

This approach gives a programmatic control at an arbitrary level of precision over filtering of dependencies to be included.

As a reference, you can see how this is used in the `license-kit` CLI in [`createScanOptionsFactory` of `scanOptionsUtils.ts`](https://github.com/callstackincubator/react-native-legal/blob/main/packages/license-kit/src/scanOptionsUtils.ts).

## Additional details

### Scanned entries

Every scanned entry exposes the license declaration in a structured form:

- `rawLicense` - the license declaration exactly as written in `package.json` (`null` if there is none),
- `license` - the parsed [SPDX License Expression](https://spdx.github.io/spdx-spec/v3.0.1/annexes/spdx-license-expressions/) (a tree of `license`, `or`, `and` and `unknown` nodes),
- `licenseIds` - the flattened list of canonical SPDX License Identifiers (empty when the license is unparseable),
- `licenseFiles` - every license file found in the package root, as `{ file, content, licenseId? }`.

Upgrading from a previous version? See the [migration guide](./migration-guide).

### License Categories

Use `parseLicenseExpression`, `renderLicenseExpression` and `classifyLicenseExpression` to work with expressions. The category of an expression follows these rules:

- **Strong Copyleft**: Licenses that require derivative works to be released under the same license (e.g., GPL-3.0)
- **Weak Copyleft**: Licenses that require derivative works to be released under the same license, but with some exceptions (e.g., LGPL-3.0)
- **Permissive**: Licenses that allow for more flexible use (e.g., MIT, Apache-2.0)
- **Unknown**: Missing, unrecognised or ambiguous declarations (e.g., `UNLICENSED`, `SEE LICENSE IN …`, `BSD`, `LicenseRef-*`)

`AND` always takes the most restrictive operand, `WITH` and `+` take the category of the base license, and `OR` follows the OR Policy passed to `classifyLicenseExpression`: `'most-restrictive'` (the default, exported as `DEFAULT_OR_POLICY`) or `'least-restrictive'` (the CLI equivalent of `--or-policy`). `classifyUnavoidableCopyleft` tells which copyleft cannot be avoided under a given OR Policy. It ignores Unknown operands, so it returns `{ category, unidentified }`: `unidentified` is `true` when an Unknown operand could require more than `category` under the OR Policy (for example `MIT AND LicenseRef-Custom`, `MIT OR LicenseRef-Custom` under `'most-restrictive'`, or a license the parser could not read), so a permissive `category` is not proof that no copyleft applies.

### Monorepo Support

`react-native-legal` scans dependencies from workspace packages with the `workspace:*` notation in your `package.json` in addition to the app's direct dependencies.

Dependencies are resolved from the directory of the scanned `package.json`, walking up the `node_modules` directories like Node.js does, so the result does not depend on the working directory the scan is run from (only a relative path to the `package.json` itself is resolved against it).

:::info
If a monorepo package is private, its name and license won't be included in the license list, but its dependencies will still be scanned and included.
:::

To also include dependencies of folders that the app does not depend on, e.g. a monorepo workspace that is not listed in the app's `package.json` or a separately bundled JS VM with its own `node_modules`, pass them as `additionalProjectRoots`:

```typescript
import { scanDependencies } from '@callstack/licenses';

const licenses = scanDependencies('./package.json', optionsFactory, {
  additionalProjectRoots: ['../../packages/shared', './backend'],
});
```

- Paths are resolved against the directory of the scanned `package.json`, and each of them must be a directory with a `package.json`, otherwise an error is thrown.
- Each additional project root is scanned like the app itself, with the same `optionsFactory` (`isRoot` is `true` for its own `package.json`); its own package is not listed.
- Do not list workspaces that the app already depends on (e.g. with `workspace:*`). They are scanned anyway, and listing them would scan them as roots too, e.g. with their `devDependencies` if `includeDevDependencies` is set to `isRoot`.

To combine the results of any scans yourself, use `mergeLicensesMappings`. It keeps a single entry per `name@version` (the entry from the first mapping wins) and combines the parent packages of all entries:

```typescript
import { mergeLicensesMappings, scanDependencies } from '@callstack/licenses';

const licenses = mergeLicensesMappings(
  scanDependencies('./package.json', optionsFactory),
  scanDependencies('../backend/package.json', optionsFactory),
);
```

### Known Limitations

#### `file:` dependencies

:::warning
This tool (and in turn, the CLI and RN plugins) do not support `file:` specified dependencies, which is a known limitation. If such packages are scanned and their dependencies (of any type) are not installed in the root `node_modules` directory, such dependencies will not be found and included.

If you would like to have support for this, please start a discussion on Github.
:::

### Default `scanOptionsFactory` value

The default value for the optional `scanOptionsFactory` parameter in `scanPackage` & `scanDependencies` functions is set to the following:

```typescript
{
  includeTransitiveDependencies: true,
  includeDevDependencies: false,
}
```

Which can be found in [`ScanPackageOptions.ts`](https://github.com/callstackincubator/react-native-legal/blob/main/packages/licenses-api/src/types/ScanPackageOptions.ts).

:::warning
This default `includeDevDependencies` behaviour is different from the default values of `license-kit` CLI's equivalent flag `--dev-deps-mode`, which is set to `root-only` by default.

To achieve the same default behaviour as in the CLI (`root-only`), set `includeDevDependencies` to `isRoot` in the programmatic API:

```typescript
const optionsFactory: Types.ScanPackageOptionsFactory = ({ isRoot }) => ({
  includeDevDependencies: isRoot,
  includeTransitiveDependencies: ...,
  includeOptionalDependencies: ...,
});
```

:::
